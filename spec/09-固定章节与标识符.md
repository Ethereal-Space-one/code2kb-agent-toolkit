# 固定章节、表头与标识符契约

本章补充[元数据协议](03-元数据协议.md)。下列章节名与表头是参考文件格式的固定部分；表格使用 Markdown 管道语法，表头后须有分隔行。单元格内不要使用未转义的 `|`。可选章节在启用对应能力时才要求存在；其表头一旦出现仍须精确匹配。其他说明性标题不受此表约束。

## 功能大纲

| 章节 | 固定表头 |
| --- | --- |
| `## 模块清单` | `\| module_id \| 业务域 \| 子模块 \| 发现入口 \| 状态 \|` |
| `## 入口证据索引` | `\| entry_id \| 类型 \| 入口或动作 \| module_id \| 证据 \| 状态 \|` |
| `## 入口受众` | `\| entry_id \| 受众 \| 范围 \|` |

`inventory_status: complete` 还须有非空的 `## 盘点覆盖说明`；这是盘点声明，不能单独证明未登记入口不存在。

## 标识符与锚点

以下是文件格式的规范写法。为读取旧项目，参考实现可能接受更宽的历史 `fact_id`，但新项目应使用 `FACT-*` 或 `F-*`。

| 标识 | 格式 |
| --- | --- |
| 仓库 ID | `[a-z][a-z0-9_-]*` |
| `module_id` | `[a-z][a-z0-9_.-]*` |
| `entry_id` | `ENT-[A-Za-z0-9-]+` |
| `fact_id` | `FACT-[A-Za-z0-9-]+` 或 `F-[A-Za-z0-9-]+` |
| `api_id` | `API-[A-Za-z0-9-]+` |
| `method_id` | `METHOD-[A-Za-z0-9-]+` |
| `intent_id` | `INT-[0-9]{3}` |
| `semantic_id` | `SEM-[A-Za-z0-9-]+` |
| `config_id` | `CFG-[A-Za-z0-9-]+` |
| `evidence_id` | `EVID-[A-Za-z0-9-]+` |

源码锚点为 `仓库ID:仓库相对路径:正整数行号`。先识别最左侧已配置的仓库 ID，再从右侧分出最后的十进制行号；中间路径允许冒号，但必须是仓库内安全相对路径。锚点可解析和行号存在，只证明定位有效，不证明该行蕴含所写自然语言结论。

`## 大纲覆盖核对` 的“已取证”目前可引用 `CODE_VERIFIED`、`RUN_VERIFIED` 或 `BUSINESS_CONFIRMED` 事实；关联关系的语义正确性仍须复核者判断。`INFERRED` 与 `UNKNOWN` 不能单独满足“已取证”。


## 独立验证者契约

以下契约只适用于策略审核的可选部分，策略 `1.0` 与信封 `0.1` 的既有行为不变。

**策略 `1.1`**：在 `1.0` 字段之外必须有且仅有一个 `verifier_requirements` 对象，`1.0` 策略不得含该字段。其字段为 `required_kinds`（不重复，取自 `external.claim_entailment`、`external.qa_replay`、`external.leak_probe`，且必须含 `external.claim_entailment`）、`min_calibration_recall`（大于 0 且不超过 1）、`max_calibration_false_positive_rate`（不小于 0 且小于 1）、`min_calibration_faults`（1 至 100000 的整数）和 `calibration_max_age_days`（1 至 3650 的整数）。`required_checks` 必须包含全部 `required_kinds`。

**信封 `0.2`**：在 `0.1` 的 `schema_version`、`subject_digest`、`module_id`、`tool`、`status`、`generated_at` 之外，必须含 `verifier{id,kind,session_id[,model_family]}`（`kind` 为 `ai`、`human` 或 `tool`）、非空且不重复的 `subject_producers`、`coverage{items_expected,items_checked}` 和 `items`。工具自行复算应查项，`coverage` 与 `items` 必须与之恰好一致：

| `tool` | 应查项 | 每项必含字段（另加 `verdict`、`reason`） | `verdict` 取值（第一项为通过） |
| --- | --- | --- | --- |
| `external.claim_entailment` | 规格 `## 入口与调用链` 中证据等级为 `CODE_VERIFIED` 的事实 | `fact_id`、`claim_sha256`、`anchors[{anchor,snippet_sha256}]` | `supported`、`unsupported`、`uncertain` |
| `external.qa_replay` | `## 问答自测` 的每一行 | `category`、`question_sha256` | `pass`、`fail`、`uncertain` |
| `external.leak_probe` | 发布清单 `## 发布文件` 中的业务文件 | `file`、`file_sha256` | `clean`、`leak`、`uncertain` |

`claim_sha256` 为去除首尾空白的结论文字的 UTF-8 SHA-256。源码片段为固定提交中该锚点行段向前、向后各扩 5 行（到文件边界为止）的原始字节，`snippet_sha256` 为其 SHA-256。非通过结论必须带不超过 300 字的 `reason`；`status` 当且仅当全部为通过结论时为 `passed`。工具不判断结论是否真实，只证明验证者检查的是同一候选、同一结论文字、同一片段。

**校准报告 `0.1`**：位于 `自动审核报告/校准/`，须已提交且与 Git HEAD 一致；字段为 `schema_version`、`verifier_id`、`generated_at`、`seed`、`pack_sha256`、`key_sha256`、`answers_sha256`、`items_total`、`faults_total`、`faults_caught`、`clean_total`、`clean_flagged`、`recall`、`false_positive_rate`、`by_fault`。校准题由同一项目的 `CODE_VERIFIED` 事实按种子确定性生成，含未改动的对照项和五类注入错误（取反、过度概括、凭空副作用、片段内注入指令、错配锚点；仅一条事实时无错配类）。结论验证者的信封须以 `calibration{path,sha256}` 引用其报告。校准结果只反映验证者在注入错误上的表现，不证明它能发现真实项目的全部错误。

**风险下限**：规格 `## 入口与调用链` 的结论文字含“权限”“归属”“金额”“名额”“指标”“状态”任一词时，下限为 `high`，否则为 `low`。该规则不理解文本，只会上调风险，未命中不表示风险低。
