# 英文使用与知识输出最小适配计划

状态：已实施，验证与边界见[实施记录](english-usage-output-report.md)。日期：2026-11-04。调查基线：Code2KB Spec 1.2.0，提交 `be50400`。

本轮按本计划实施；本次作为 1.2.0 后续补充发布，不修改既有发行标签或工程版本号。计划面向公开项目，不引用使用方的私有代码、业务数据、路径或版本。

## 1. 交付目标

英语用户可以只按英文操作说明，把任务交给自己的 AI 编码助手，完成配置、范围盘点、代码取证、英文知识写作、审核和发布；得到可供英文机器人检索的业务知识。

继续使用一套 CLI、一套事实与证据规则、一套审核流程。首期支持简体中文和英文，每个知识项目选择一种知识输出语言，不同时维护两套翻译正文。

首期的英文支持边界：

- 用户交互、操作指南、业务正文、研发说明文字，以及工具生成的导航、边界说明和检索单元说明可以使用英文。
- 现有协议文件名、内部固定章节、表头、枚举、ID、JSON 键和命令保持原有写法；英文指南解释其含义，由 AI 填写。研发材料中用于校验的固定标签仍可能是中文。
- 不承诺所有文件路径、内部表格和 CLI 报错都已英文化。英语用户无需自行翻译这些标识，但直接操作终端时仍可能遇到中文诊断；AI 应解释诊断，不能绕过检查。
- 不改变源码语言覆盖范围；不引入机器翻译服务、模型 SDK、机器人部署或新的检索引擎。

## 2. 必须修复的实际阻碍

| 已核对事实 | 对英文使用的影响 | 最小处置 |
| --- | --- | --- |
| 英文 README 后续链接主要指向中文指南；Skill 与任务契约主要为中文 | 英语用户没有完整的英文使用说明 | 增加英文使用指南和精简的英文 AI 执行指引，沿用一个 Skill 入口 |
| 任务提示示例明确要求“生成中文业务正文” | 即使用户使用英文提问，指令仍可能把产物拉回中文 | 改为遵守项目输出语言，缺省行为保持中文 |
| `make_release`、`retrieval_index`、`current_markdown` 等直接生成中文 | 英文正文发布后，导航和边界说明仍混入中文 | 用小型固定文案映射生成英文展示文字，路径不变 |
| 检索构建的通用标题、共享条件标题和未知识别主要依赖中文 | 英文标题可能把适用条件与回答拆开，未知项提示可能漏识别 | 补充指南约定的英文标题与未知表述，保留保守合并规则 |
| 独立验证者策略的风险下限匹配中文词 | 英文高影响结论不会触发同一组词面风险规则 | 增加有限的英文规则与正反例；仍声明不理解语义 |
| 业务版禁用表述包含大量中文词 | 英文实现细节或过程表述可能绕过对应词面扫描 | 补充明确的英文技术与过程短语，避免封禁普通业务词 |

只读复现结果：英文示例含 `Applicability`、问题和 `Unverified outcomes` 三节，当前 `index_sections` 返回三个独立单元；`unknown_lines` 返回空集合；含 `Permission`、`ownership`、`status` 的结论得到风险下限 `low`；`The internal endpoint uses a transaction annotation.` 未被业务禁用表述规则命中。该复现定位规则缺口，不代表已验证真实机器人回答或泄漏结果。

## 3. 用户流程

1. 按英文指南安装工具，准备 AI 编码助手和固定提交的源码仓库。
2. 创建独立知识项目，配置仓库、提交、输出位置和 `content_language: en`。
3. 将英文启动提示交给 AI；先报告范围、模块和缺口，再逐模块取证。
4. AI 按固定协议写内部规格；业务正文、研发说明及问答使用英文，保留条件、失败和未知。
5. 完成现有检查与候选准备，再按人工审核或已有预授权策略审核推进；语言选择不授予发布权限。
6. 经授权发布并审计；需要检索扩展时，生成英文单元并运行英文问题集。
7. 用户将已发布业务知识接入自己的 FTS 或向量索引；机器人回答仍由下游系统负责。

交互语言由用户任务决定，不额外建立 `ui_language` 配置。输出语言与交互语言可以不同；源码的编程语言不决定二者。

## 4. 实施需求

### EN-01 英文操作与 AI 入口

- 新增 `docs/usage.en.md`，覆盖安装、配置、启动提示、盘点到发布、可选检索，以及固定协议标识的英文对照。
- 在现有 `SKILL.md` 添加简短的中英文入口说明；英文任务按需进入一份精简英文执行指引，不复制整套 Skill、状态机或全部参考文档。
- 英文指引必须涵盖固定提交、入口覆盖、条件与未知、业务与研发隔离、四类自测、影响复核、审核授权和发布审计。字段细节仍以现有规范与模板为准。
- 英文指南提供可复制的启动任务和一个最小文件示例。固定中文标签视为协议标识，给出英文解释；不要求用户自行翻译表头或文件名。
- 既有详细中文参考继续供 AI 按需读取；用户无需逐份阅读。首页须说明英文支持边界，不能仅因已有英文 README 就宣称全部文档已双语化。

### EN-02 一个输出语言字段

在现有 `知识库配置.json` 增加可选字段：

```json
"content_language": "en"
```

规则：

- 只接受 `zh-CN`、`en`；缺省为 `zh-CN`。未知值、空值或错误类型拒绝，不猜测操作系统语言。
- 复用现有知识配置，不增加第二份语言配置、CLI 同义参数或工程配置版本。
- 可发布的业务、研发知识文件增加可选的同名 front matter 字段，作为该文件的输出语言声明；缺省同样解释为中文。英文模板示例写 `content_language: en`。
- 配置是写作目标，文件字段是被审核正文的一部分。两者不一致时，新候选和发布必须拒绝；只改配置不能把既有正文认定为已翻译。
- 文件字段进入原有正文摘要和候选摘要；更改它或翻译正文后，沿用 `impact`、复核、`prepare --refresh` 和重新审核，不建立新的审批体系。
- 一个项目首期只发布一种语言；源代码标识、产品名、引用原文等不强制翻译。不用“不得出现汉字”判断英文正确性。

这是公开元数据的增补，需要更新允许字段、模板说明和兼容文档；不能声称格式完全未变。不改变当前文件协议标识、版本清单和指针 Schema。旧中文项目无需迁移；新英文字段需要支持本能力的 CLI，旧 CLI 的未知字段拒绝机制不放宽。

### EN-03 英文正文与生成展示

- AI 直接从证据编写英文正文，不在批准后调用模型翻译，也不自动翻译既有发布物。
- 业务正文的标题、段落、问答、关键词和未知说明使用英文；每个可回答段落保留适用条件、失败和未知。
- 研发说明使用英文，固定 API/METHOD 表头和详细字段标签保留现有协议写法；事实、接口、方法 ID 与证据锚点不翻译。
- 对目录、已发布大纲、发布信息、事实编号对照、检索索引和当前版本说明增加小型文案映射。英文导航用 `Overview`、`Rules and limitations` 等展示名，不直接把中文文件名当链接标题。
- 固定文件名、路径和链接目标不变；业务与研发两版复用同一份业务正文，继续逐字一致。
- 工具中直接生成可检索说明的已有渲染函数一并盘点；只替换展示文案，不增加一套英文渲染流程。不涉及用户路径的 CLI 帮助和全部错误翻译延后。

优先形成一个公共的小型语言辅助模块，集中管理支持值、生成文案和必要标题别名；不引入通用国际化框架、插件系统或运行时翻译依赖。

### EN-04 检索与检查保持相同边界

| 位置 | 适配要求 |
| --- | --- |
| 检索分块 | 对 `Applicability`、`Answer boundaries`、`Unverified outcomes` 等约定标题应用现有共享上下文规则；不能把条件和回答安全拆开时保留整篇 |
| 标题与问题 | 支持指南采用的英文 `Q:` 问题形式及通用标题；不要把每个普通英文标题都误认作问题 |
| 未知提示与比较 | 识别约定的 `unknown`、`not verified`、`cannot be determined` 等表述，大小写处理一致；不要把任意否定句当未知 |
| 检索单元展示 | 模块说明、结论与边界、出处标题提供英文形式；构建、合并、读取、审计和评测共用同一定位规则，消除散落的中文字符串切分 |
| 风险下限 | 对权限、归属、金额、名额、指标、状态补明确英文词或短语和词边界；两种语言及混写都可触发，不根据语言选择关闭另一组规则 |
| 业务版扫描 | 补明确实现或过程短语；`account`、`order`、`status`、`permission` 等正常业务词不得仅因英文而禁用。保留源码链接、内部 ID 等已有规则 |
| 已启用的独立验证 | 验证任务说明和校准题的取反、过度概括、虚构副作用等生成文案支持英文；不改变题型、报告字段、校准计分或审核授权 |

检索扩展从已审计的基础正文及其语言声明决定展示语言，不从之后被修改的项目配置猜测。检索单元的机器字段和 ID 算法不变；不增加一份英文路由索引或中英交叉检索机制。

规则仍是词面辅助，不证明完整语义、披露安全或真实权限执行。新规则只用于对应新候选和新发布的检查；历史发布审计按冻结正文是否显式声明语言区分词面规则，无语言声明的旧发布沿用原规则，不能因加入英文规则使原本有效的冻结发布物被重新否决。

## 6. 验收与必要回归

采用一个自行编写的公开小案例：同一模块具有入口条件、正常结果、失败分支、配置取值未知和高影响权限条件。预期答案及证据先人工定义，再运行工具，避免从实际输出反填预期。

| 验收 | 要证明什么 |
| --- | --- |
| 旧项目缺省 | 不填新字段仍按中文处理；不需要重写既有正文、审核记录或发布物 |
| 配置与语言绑定 | 非法语言被拒绝；英文配置与缺省中文文档不一致被拒绝；改语言不能沿用旧候选批准 |
| 英文基础链路 | 英文正文完成检查、影响复核、候选审核、双版发布及审计；两版共有业务正文逐字一致 |
| 英文检索链路 | 构建、评测、审计、查询全部走通；实际调用现有 FTS5 适配器验证代表性英文问题，而非只查关键词表 |
| 条件与未知 | 召回的首个证据单元带必要条件、失败和未知；删除未知边界能被现有覆盖比较的英文规则发现 |
| 检查不绕过 | 英文高影响结论触发同类风险下限；英文实现细节进入业务文件被拒绝；正常英文业务描述仍通过 |
| 可选验证链路 | 英文证据包与校准题可读；候选、源码片段、覆盖、报告及校准摘要仍按原规则绑定，改动报告不能通过校验 |
| 历史与冻结输入 | 现有历史审计夹具仍通过；基础发布后修改配置，不改变该发布的英文检索依据和语言 |
| 文档与公开内容 | 英文入口可达，链接有效；新增内容不含使用方私有信息；产物语言抽查不以文件数量或无汉字替代语义审阅 |

四类问题至少覆盖正常、失败、未知和权限边界；只记录真实执行过的检查。FTS5 测试验证召回证据，不宣称验证了问答模型的最终答案，也不启动无关框架或生产服务。

回归安排：文档阶段只审文案和链接；程序阶段运行受影响正反例；候选合并／发行前运行一次既有全量测试及 Python 3.9–3.13 CI、公开内容和兼容检查。发现新问题后只重跑受影响检查，避免每改一段文案重跑全库。

## 7. 实施顺序与结束条件

1. **入口与字段**：完成英文指南、精简执行指引和输出语言规则；确认固定协议标识保留，不产生两套流程。
2. **最小程序适配**：实现语言读取、候选一致性、生成文案和英文词面规则；先修复上述可复现缺口。
3. **一个完整案例**：完成英文知识发布与 FTS5 证据召回，核对条件、未知、审核失效和历史审计。
4. **交付说明**：按实际结果更新中英文首页与兼容说明；按本次作为 1.2.0 后续补充发布，不跟随任何私有工具版本。

完成标准是：英语用户按英文指南，不自行翻译模板、不修改程序，即可让 AI 产出并发布英文业务知识；检查与检索不会因改用英文而静默跳过本轮已适配的边界。保留中文协议标识和部分中文诊断作为明确的首期限制，不宣称已支持任意人类语言或完整终端国际化。

## 实施补充：读者与语言隔离

用户要求防止人读与 AI 读混淆：`docs/usage.md` 与 `docs/usage.en.md` 只面向维护者；`SKILL.md` 只负责选择一个交互语言的 AI 指引，分别进入 `chinese-workflow.md` 或 `english-workflow.md`。两份指引明确禁止把操作指令当作知识正文。机器协议标识保持原样，不建立另一套英文协议；输出语言由配置和被审核的正文声明绑定。
