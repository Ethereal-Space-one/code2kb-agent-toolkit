# 2.4.0 验收与发布清单

发行日期：2026-11-16。本文记录可复现边界、本地验收及发行核对要求；远端 PR、CI、标签和产物状态以对应平台记录为准。

## 本次落地范围

- 可选作者填写 UI 章节，严格结构及本模块 FACT/ENT 引用检查；不新增知识文件类型或基础协议。
- 只读双版候选生成，显示/启用/忙碌不相互替代，外部交互不被渲染成必然打开或执行成功。
- UI 内容加入按事实的影响依赖；多个控件可共享入口/区域，导航目标登记变化触发相关事实复核，无关事实及未启用项目摘要保持稳定。
- 四控件固定源码、九条静态事实、状态与转换、独立 FAQ、源码片段、候选、模拟复核/批准、双版、检索、旧快照保护及重新审核发布生命周期。
- 六条订单的有界集合参考案例，九条事实、八个入口、七个设计检索问题及十个改述回归问题。沿用既有正文/检索，不新增集合 schema、适配器或任务引擎。

## 验收分层

| 层次 | 验证方式 | 不证明什么 |
| --- | --- | --- |
| 结构与引用 | 严格 JSON、重复/类型/身份/引用反例，共用 check/preflight | 事实蕴含、条件逻辑完备性 |
| 源码与精确集合 | 固定摘要、实际临时 Git 提交、片段快照、纯内存集合运算 | 真实应用、服务、权限或设备 |
| 作者交互记录 | 静态源码对照、双版候选、同名按钮及隐藏/启用维度隔离 | 自动提取、框架运行或跨设备幂等 |
| 发布与维护 | 测试专用批准、双版/检索审计、失效门禁、旧文件摘要、新快照 | 真实项目批准或现实审核独立性 |
| 检索与组装 | 实际检索原文、必要条件/未知、单单元完整性、故意裁剪的诊断反例 | 最终模型配对正确或线上质量 |
| 独立回答重放 | 导出十题的实际上下文与独立答案键，另留存原始回答和逐项判断 | 未运行模型时不登记模型成绩；公开回归题不是新留出题 |

## 可复现检查

在仓库根目录执行[标准发布检查](release-process.md)。本版本还执行以下专项检查：

```bash
python3 -B -m unittest discover -s validation/tests -p 'test_ui*.py' -q
python3 -B -m unittest discover -s validation/tests -p test_collection_scope.py -q
python3 -B validation/tests/test_ui_behavior_release.py --export-fixture /tmp/code2kb-ui-example
python3 -B validation/tests/test_collection_scope.py --export-fixture /tmp/code2kb-collection-example
python3 -B -m unittest discover -s scripts -p test_package_plugins.py -q
```

导出目标必须为空。上述临时源码提交与测试批准不回填到真实项目，不把导出目录或模型调用日志提交到仓库。

## 本地执行记录

本地 Python 3.12.14 与 3.13.5 的完整单元测试均为 314 项通过；聚焦 UI 为 22 项、集合为 5 项、插件打包回归为 5 项通过。规范及覆盖映射 67/67，一致性 4/4，关系 2/2；合成检索规模 96/96、120 单元，无受众泄漏。链接、公开内容、版本边界、编译、空白、最小示例及固定公开源码 runner 检查通过。

已在全新虚拟环境安装本地 2.4.0 包，并在仓库外确认版本及 `render-ui-facts` 帮助入口。两个夹具均成功导出实际固定源码、审计发布及查询证据；没有运行前端或回答模型。发行准备时，三个宿主归档已从冻结候选提交构建并审计；正式发行仍须从最终发行提交重新构建，不能复用旧候选归档或把工作树检查等同于固定提交产物校验。

本地验收未覆盖 Python 3.9–3.11，正式发行要求远端 Python 3.9–3.13 与插件 CI 全部通过；上述本地结果不替代远端记录。

## 发行核对顺序

1. 冻结改动，跑完整单测、规范/67 条覆盖映射、一致性、版本边界、关系、检索规模、链接、公开内容、示例、编译和空白检查。
2. 在全新虚拟环境安装本地包，在仓库外运行 `code2kb --help`、`--version`，并验证 `render-ui-facts` 入口；按固定提交构建/审计三个宿主插件，检查版本均为 2.4.0。
3. 将源码与测试、文档/版本更新分为清晰的本地提交，审阅相对当前公开基线的完整差异。未获授权不推送、开 PR、打标签或上传归档。
4. 获准后从发行分支开 **draft PR**，说明可选能力、兼容限制及证据边界；确认远端 HEAD 与审阅 SHA 一致，等待 Python 3.9–3.13 和插件 CI。
5. 维护者复核并批准合并到受保护 `main`；本地通过不等于远端 CI 或 merge-ready。正式发行前，将 CHANGELOG、ROADMAP 和兼容矩阵三处待发布状态同步为正式状态，更新 README/发布说明中的候选表述及发布日期，再完成检查与审阅。
6. 在取得发行及关联 npm 流程授权后，从已通过 CI 的 `main` 提交创建不可移动 `v2.4.0` 标签和同版本 GitHub Release。**标签流水线会触发 npm 发布**，不是仅作本地版本标记；发布前核对受保护的 `npm-release` 环境、包身份、版本及同提交构建产物。
7. 验证 GitHub 标签/Release、npm 版本和 dist-tag、插件索引/安装入口，使用全新目录重复快速开始；无确认结果不声称发行完成。

## 已知限制与停止线

- 只提供作者填写扩展，不做 AST/DOM 自动提取、运行模拟、状态可达性证明或通用工作流执行。
- UI 仅关联本模块事实/入口，导航不跨模块；集合例子仅六条固定记录，批量/导出返回目标编号，不执行服务或交付文件。
- 机器校验不判定自然语言与证据的全部语义，事实存在不能为权限、请求、持久化或业务完成背书。
- 无章节旧项目保持原行为；启用 UI 必须用 2.4+ 维护，旧工具不具备该扩展的引用与失效保护。
- 本地可用 Python 版本上的通过，不替代完整 Python 3.9–3.13 远端 CI、真实平台运行或生产项目验证。
