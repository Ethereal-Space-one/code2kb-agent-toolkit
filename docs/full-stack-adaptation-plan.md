# 全栈与跨语言取证适配实施计划

状态：已实现，验证结果见[实施记录](full-stack-adaptation-report.md)。日期：2026-11-04。调查基线：Code2KB Spec `1.2.0`，提交 `83c171f`。

本文件保留实施范围和验收约定；结果单独记录。工程发行版本在兼容性核验后确定，不调整现有路线图的版本编号。

## 1. 目标与适用范围

让 AI 使用同一套证据规则，从不同语言、源码布局和系统形态中提取业务行为与实现逻辑，生成供检索问答使用的知识。适用形态包括浏览器与移动端、服务端渲染、单体与微服务、后台任务、共享库及构建部署材料；按实际项目选择相关场景。

“全栈适配”的验收含义：

- 通用盘点不以编程语言白名单、目录名称或固定目录深度代替源码范围判断；不能解析的文本仍可进入 L1 盘点，并明确能力边界。
- 取证按页面、客户端、服务、任务、数据和支撑依赖的实际职责展开，不把某种语言固定归为前端或后端。
- 跨层、跨仓和跨语言的连接需要两侧契约与版本依据；名称或路径相同只产生候选。
- 结论能回答业务问题，并保留条件、失败与未知；文件数和语言标签数不作为语义适配完成率。

本计划独立维护于开源仓库，使用公开或自行编写的通用案例。不引用使用方私有路径、版本、源码、业务数据或测试结论，不引入使用方的协议编号。

| [范围参考](../skills/extract-app-knowledge/references/范围与大纲.md)已有入口和受众规则，但缺少仓库边界、重复检出和构建版本的系统调查步骤 | 同名仓库、共享库或非标准源码目录容易被误合并、漏登记或错误配对 | 补通用根范围与依赖盘点 |
| [取证参考](../skills/extract-app-knowledge/references/模块取证与规格.md)已有字段闭环，但异步受理、消息确认、配置覆盖和异常清理的共同问题分散在技术细节中 | 只读表层入口可能把受理写成完成、把默认配置写成最终值 | 补跨语言场景问题，复用既有事实与未知记录 |
| [接口与方法校验](../validation/knowledge.py)把引用不存在、缺少反向关联统一报为“关联不一致” | 使用者无法从报错直接判断应修改哪张表、哪一侧关联 | 保留通过条件，细分诊断 |

上述是可定位的范围、提示词和诊断缺口；不据此宣称已证明检索命中率或建库工时提升。

## 3. 分层方式

| 层次 | 承载内容 | 加载规则 |
| --- | --- | --- |
| 通用范围层 | 仓库、构建单元、系统角色、入口和缺口 | 开始范围盘点时读取 |
| 通用场景层 | 跨层契约、异步状态、资源生命周期、配置与运行边界 | 仅在链路出现相应场景时读取 |
| 技术栈适配层 | 对应语言、框架或平台的具体查找线索 | 以实际源码和构建声明为依据选择；保留现有指南路径 |
| 工具层 | 固定提交扫描、引用与证据校验、诊断 | 能力分级和候选状态沿用既有契约 |

通用参考给出“需要回答什么”，适配指南补充“在该技术栈中去哪里查”。不为每种语言复制一套完整流程，不建立一个必须全量加载的技术大全。

## 4. 实施需求

### FS-01 通用范围盘点

拟新增 `skills/extract-app-knowledge/references/全栈范围盘点.md`，由盘点契约按任务指向该参考；既有大纲继续承担正式入口、模块、受众和范围记录。

具体步骤：

1. 先明确目标读者、业务问题与授权根范围，区分范围内、关联影响及范围外对象。
2. 识别 Git 仓库、worktree、子模块和多仓检出边界；发现的仓库先登记，正式取证前须进入项目配置并固定提交，不自动扩大取证权限。
3. 按源码与构建材料识别应用、服务、库、任务和构建模块，不要求使用固定 `src` 路径。同一仓库可以承担多个职责，同一运行单元也可能涉及多个仓库。
4. 区分仓库检出数量、独立仓库和服务数量。同名或相同树只提供复用线索，仍保留路径与固定提交对应；版本不同分别核查。
5. 把依赖声明、锁定版本、源码调用、部署声明及运行观测分别记录。依赖名称与本机同名源码不能单独证明实际使用的版本。
6. 按实际存在的页面、交互、HTTP/RPC、消息、回调、定时和命令等入口进入既有大纲；没有独立业务入口的共享库只作支撑关系，不虚构模块或入口。

需要复杂定位时，在参考中提供一个可选的内部工作索引示例：对象、职责、仓库及固定提交、关系类型、证据位置、缺口。示例放在知识源和发布目录之外，只引用既有事实，不增加正式文件类型、必填表或第二份事实台账。

### FS-02 跨语言场景取证

拟新增 `skills/extract-app-knowledge/references/跨语言场景取证.md`，从模块取证契约和相关适配指南按需引用。只对影响业务回答的路径展开：

| 场景 | 通用取证问题 |
| --- | --- |
| 界面与平台 | 页面可见、按钮可点、请求实际发出、服务端授权是否为不同条件？客户端和服务端渲染职责在哪里？平台差异有什么源码依据？ |
| 跨层与跨仓契约 | 调用条件、参数构造、序列化、路由重写、服务处理和返回结构如何衔接？接口与实现是否分离？双方版本能否配对？ |
| 分支与状态 | 枚举定义是否都有处理分支？默认、未识别值和异常分别进入何处？提示、受理、持久化和最终状态是否一致？ |
| 异步与消息 | 入队、接收、确认、业务完成和通知发生在什么时点？失败重试、幂等、上下文传播、失败去向及取消如何影响结果？ |
| 数据与原生依赖 | 数据读写和事件消费如何闭环？外部程序、原生库、文件、连接等资源由谁管理？正常、异常及取消路径如何清理？ |
| 配置与运行 | 默认值、绑定、覆盖、装配条件和实际取值分别有何依据？构建或部署声明能证明到哪里？哪些结果需要运行证据？ |

实施约束：

- 在既有规格、接口、方法、匹配状态和待确认事项中记录结果，不新增强制语义表。
- 通用步骤使用“赋值或更新、数据映射、拦截与包装、注册与生命周期”等表达；setter、ORM/XML、特定框架注册器等作为技术栈示例。
- 修订 PHP 和 UniApp 指南中的 Java 绑定，并明确默认目录及框架约定仅是调查线索；Java 特有的构建、RPC 和注册机制留在 Java 指南按需说明。
- 同名路由、Topic、表名或包名只支持发现候选；不能据此把跨语言关系标为已匹配。
- 保留现有问答表头，补充设计案例与真实使用问题的来源说明。“通过”明确指本次静态对照，不能代表机器人拒答或线上权限已经执行。

### FS-03 显式扫描范围改进

优先复用现有 `analyze-candidates --candidate-schema 0.2 --scope ...`，不增加全局包含规则、任意插件加载或新的配置顶层字段。

规则设计：

1. 未指定 `--scope` 时，现有目录过滤和扫描默认值保持不变。
2. 指定安全的仓库内文件或目录时，显式范围路径本身及其祖先中的默认过滤目录名称不再使整段范围被跳过。例如 `--scope vendor/internal` 应能盘点其中受版本控制的自有源码。
3. 显式范围之下新遇到的生成物或依赖目录继续沿用默认过滤。例如上例下的 `vendor/internal/node_modules` 仍被过滤；需要调查该子路径时再明确指定更窄范围。
4. `.git` 元数据、越界路径、非普通文件、符号链接、二进制、非 UTF-8、文件大小与数量限制不因显式范围而放宽。子模块 gitlink 保留跳过记录，由 FS-01 指导作为独立仓库登记，不在扫描器内自动递归工作区。
5. 候选仍读取固定 Git 提交。未知后缀保留为 L1、`language: unknown`；不按扩展名白名单删除候选，不把保留文本宣传为结构或语义分析。
6. 两个内置 Adapter 的候选格式 `0.2` 共用该范围规则；旧默认候选格式 `0.1` 不变。已存在路径的候选 ID 规则保持稳定，必要时更新 Adapter 规则版本以标明扫描语义变化。

复用现有 `snapshot.scope` 和 `coverage.skipped` 解释范围与过滤结果，不改变严格输出字段集合或公共 SDK 的方法签名。若实施中发现需要新增参数、字段或兼容变更，先更新本计划评审后再实现。

### FS-04 引用说明与诊断改进

在现有取证参考和规格模板中解释：API 与 METHOD 必须双向关联，多 ID 使用英文逗号；关联索引不等于直接调用图。实际调用的顺序、条件及直接或间接关系写入研发正文，不为满足校验虚构调用。

工具保留原有通过条件，区分四类错误，并在错误中提供知识文件位置、API/METHOD ID 以及应检查的列：

| 错误 | 应提供的诊断信息 |
| --- | --- |
| API 引用了不存在的 METHOD | 缺失的方法 ID，引用它的 API，检查“方法职责”表 |
| METHOD 存在但没有反向关联该 API | 方法 ID 与 API，缺少“关联接口” |
| METHOD 引用了不存在的 API | 缺失的接口 ID，引用它的 METHOD，检查“接口契约”表 |
| API 存在但没有反向列出该 METHOD | API 与方法 ID，缺少“主处理方法”关联 |

合法、无关联、格式错误、重复 ID 和原有其他校验规则保持不变；错误仍使用现有异常和失败响应，不引入新的机器错误分类契约。

## 6. 验收：检查真实失效机制

### 6.1 确定性工具验证

- 默认扫描仍过滤普通依赖目录；显式指定自有 `vendor/internal` 后应返回对应文件，不能再次得到无解释的零结果。
- 验证整仓、目录、单文件、相似前缀路径及显式范围内嵌套生成目录；文件不得越出约定范围。
- 选择 Rust 等已标注语言、未登记后缀的 Elixir 等文本和无后缀构建文件验证 L1，不为每种后缀复制同一个测试。
- 拒绝或按现有分类跳过路径穿越、符号链接、gitlink、二进制、非 UTF-8 和超限文件。修改工作树后重扫同一固定提交，结果须保持一致。
- 对同一有效规格分别注入上述四类关联错误，核对拒绝结果和定位信息；再确认多对多关联及无接口任务仍通过。测试只覆盖已变化的分支，不增加镜像实现的断言。

### 6.2 跨语言取证演练

以可公开、自包含的源码片段和固定提交构造三个不同问题，而非启动多套框架或统计语言数量：

| 演练 | 应核对的知识结果 |
| --- | --- |
| 浏览器客户端 → 不同语言服务 → SQL／配置 | 界面限制与服务端校验分别记录；请求或响应变换有两端依据；配置默认值与运行值分开 |
| PHP 服务端页面 → 另一语言后台任务／消息契约 | PHP 按实际职责取证；受理、确认、完成和重试不混写；不匹配的契约保留未知 |
| 主程序 → 原生组件／外部命令 → 文件与构建材料 | 正常与失败的副作用及资源清理有证据；二进制内部行为与部署状态保留未知；包含非标准源码目录 |

先确定案例的预期分支、锚点及必须保留的未知，再进行 AI 取证与正文复核，避免从工具输出反填预期。沿用既有规格、双版和可选检索流程，检查召回内容是否携带决定答案的条件与边界。

新增指南的验收依赖上述案例中的实际知识结果，不用“提示词中出现了关键词”或 `check` 通过代替语义审阅。演练不证明所有语言具备同等结构分析能力，也不冒称生产服务或最终机器人回答已经验证。

### 6.3 必要回归节点

1. 通用指南与模板阶段：审阅按需加载、角色划分、条件与未知；检查链接和公开内容，不重复跑整套代码测试。
2. 扫描及诊断阶段：运行受影响测试和 CLI 正反例，处理发现的回归。
3. 候选合并／发行阶段：按仓库既有 CI 一次完成 Python 3.9–3.13、全量测试、规范与一致性、历史发布审计、检索关系、版本边界、链接、公开内容和安装验证。只有新变化或失败才重跑相关检查。
