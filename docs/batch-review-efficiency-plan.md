# 批次复核与交付效率优化实施计划

状态：本地实现、回归与回放验收完成；已获授权作为 2.0 主分支补充推送，按 PR 与 CI 流程交付。原始标签不变。

日期：2026-11-09。

适用项目：Code2KB Agent Toolkit。规划基线为工程 2.0.0、提交 `8d54fe8`；实施前重新核对 HEAD、工作区及本计划引用的代码。工程版本在发布准备时确定，本次不改版本号或知识文件协议。

## 1. 目标与证据边界

减少多模块知识提取中同一稳定输入的重复检查、审核交接中的重复抄录，以及直到准备发布包才发现的结构返修。优化对象是语言无关的知识生产流程，适用于单仓、多仓及混合技术栈；不新增 Java 专用路径。

当前公开实现可直接确认的事实：

- [命令入口](../validation/knowledge.py)在处理模块级 `impact` 之前读取项目并执行公共校验；指定模块不等于只读取该模块。
- `check` 的 `pending_claim_impacts` 来自全局 `governance.impacts()`。相同稳定输入上，成功检查且该字段为零后，再逐模块获取空队列会重复工作。
- [影响队列](../validation/governance.py)检测结论、正文、已登记影响关系的增删改，并纳入已启用的关系映射复核。它不能发现所有未登记的语义依赖。
- `prepare` 还执行候选文档集合、来源基线、目录和调用匹配等检查；普通结构检查不能替代其全部条件。
- [续跑指导](../skills/extract-app-knowledge/references/长任务续跑.md)仍以逐模块执行 `check`、`impact` 等描述循环，存在批次工作下重复解释和调用的空间。
- [现有执行器](0.6.0-runner.md)已有任务账本、检查点、项目锁与恢复机制，不需要另建一套状态系统。

以上是优化理由，不是提速测量。本计划不引用私有项目的路径、业务名、源码、运行日志或耗时数字；公开收益结论只来自后续可重现的公开或合成样本。

## 3. BR-01：批次检查与复核闭环

### 3.1 推荐顺序

1. 明确本批模块、所有者、共用事实及已知消费者。作者只写分配范围，共享资料由主控维护。
2. 模块冻结后可开始该模块的源码与正文复核。全局检查前停止正式输入的写入并核对冻结状态。
3. 批次输入稳定后执行一次全局 `impact`，保存原始完整结果，按结果中的 `module_id` 分派实际条目。初始待复核数量由该队列提供，不额外为取同一数量再跑 `check`。
4. 审核发现集中返修。复检覆盖修改、原发现及实际消费者；旧队列不再描述变化后的输入。
5. 全部必要语义复核完成后，逐模块执行 `confirm-claims` 和 `prepare`。不为取得空队列而提前确认。
6. 所有确认和准备操作完成、正式输入再次稳定后执行批末全局 `check`。退出成功且显式 `pending_claim_impacts == 0`，可以收口该项影响检查；不再逐模块获取末次空队列。
7. 若数量非零，展开全局真实队列；若检查失败或字段缺失，不以成功日志、旧计数或人工补值代替。定位并处理后重新检查。

全局 `impact` 不是完整验收；`check` 通过也不是内容批准。入口覆盖、审核快照、检索及发布等必要门禁仍分别执行。

### 3.2 结果复用的有效期

复用的是已有检查的证据，不是缓存授权。现有批次记录至少关联：

- 工具版本或代码提交、命令及参数、带时区起止时间、退出码和原始输出位置；
- 知识项目 HEAD，以及实际被读取的配置、大纲、正式文档、关系、证据、清单等输入的路径与字节摘要；包含新增、删除及未跟踪正式文件；
- 配置中的固定源码提交，以及影响配置解析的环境变量解析值等外部输入；不得记录凭据；
- 未关闭问题、队列条目、审核依据与下一步。

只记录 Git HEAD 不足以绑定未提交输入。检查前后输入集合或摘要不一致时废弃本次结果；禁止在仍有正式写入者的工作区执行全局验收。现有项目锁不约束任意外部编辑器，不能单靠持锁声称输入稳定。

确认和准备命令可能修改规格或清单，因此先前检查不能认证其后的状态；批末检查必须读取最后状态。存在证据或策略有效期时，不跨有效期复用。上下文恢复或更换执行者继续按既有恢复规则核对当前文件并执行必要检查，不引入长期复用通行证。

使用已有记录或检查点保存上述信息；第一轮不设计新的强制协议或运行数据库。

### 3.3 返修范围

- 只改模块内正文且已核实没有外部消费者时，可只重取该模块队列；这仅减少队列范围，不宣称当前 CLI 已变为局部扫描。
- 共用事实、跨模块关系、来源基线或消费者发生变化时，覆盖相关消费者；不能只按编辑过的文件选择模块。
- 配置、大纲或其他全局输入变化、依赖未登记或范围无法可靠判断时，退回全局检查。
- 删除事实和引用时，必须核对旧答案及旧消费关系的处理，不能因条目消失就认定审核通过。

## 4. BR-02：只读结构预检

### 4.1 交付与接口

已增加薄 CLI 入口 `code2kb preflight --project-root <project> --module-id <id>`，用于交稿前检查本模块的候选结构；实现范围与原计划的收敛见第 11 节。

默认检查当前模块全部候选正文；如暴露文件选择或检索元数据参数，必须与 `prepare` 共用选择和解析规则。预检不要求已执行 `confirm-claims`，因此可以在语义审核前调用；它明确不判定内容审核完成、策略有效或模块可发布。

结果通过既有 CLI 响应方式返回，并明确检查范围、已执行项、问题位置、跳过项和后续仍需执行的步骤。缺配置、缺基线、无法解析等情况报错，不伪装成预检通过。仅供上下文检查而尚未完成的其他模块不得导致目标模块无从预检；全局一致性检查仍由正式命令负责。

### 4.2 复用规则

先把 `prepare` 中可在未确认草稿上执行的无副作用检查提取为共用函数，正式 `prepare` 与预检调用同一实现：

- full/compact 配置下的候选文档要求与必需元数据；
- 模块规格、研发文件的来源版本一致性；
- 接口/方法目录与规格的对应、调用匹配表一致性；
- FAQ 标题等现有导航结构要求，以及范围内的局部链接检查；
- 提供了检索元数据时，沿用现有格式和受众边界检查。未提供时显式标为未检查，不自动编造。

需要上下文时读取必要配置、大纲、相关规格和固定源码；不能为了速度省略所执行检查的必要输入。若某项只能全局判断，应标明不在模块预检范围内，由正式流程检查，不能另写弱化版本。

预检只读取、不写审核状态、结论投影、发布清单、批准记录或发布目录；不得调用真实 `prepare` 后再撤销写入来模拟只读。实现中不得通过跳过正式检查换取提速：`prepare` 仍按当前输入完整重验，不接受旧预检报告作为放行凭据。

不新增第三方依赖，不重构与预检无关的发布事务。若抽取检查需改变既有审核或发布语义，停止扩大实现，先报告冲突，再决定范围。

## 5. BR-03：可选滚动独审与续跑

- 一个模块冻结即可交给未参与该稿生产的审核者；遵守现有审核模式对身份声明、独立验证和授权的要求，不把换会话视为现实身份已认证。
- 审核绑定冻结稿。全局队列尚未生成时可先复核源码与正文，之后补实际消费者和变化范围，不机械重审全部正文。
- 作者冻结稿、真实队列分别保留一个可定位版本。后续交接引用原件与摘要，各自记录实际判断；不得将可变路径当作固定证据。
- 主控集中处理未关闭发现、冲突、高影响结论和验收门禁。无新增依据时不把第三遍全文重读设为必经步骤；有实质疑点仍应扩大复核。
- 使用现有进度记录或可选 runner 账本作为唯一接续入口。检查点存状态、证据指针、冻结状态及下一步，不复制完整正文和队列。
- 阶段切换和恢复时读取当前任务所需规则及证据；不设置按工具次数机械重读全部规范的制度。
- 单执行者模式继续可用；不强制用户具备多代理能力，也不自动批准或发布。

## 6. BR-04：现有流程的小范围补充

### 候选检索

将已有候选构建或 staging 检索评测路径放到内容批准前的质量检查中；使用隔离候选，不覆盖当前发布。固定问题、预期受众与来源、排名范围，保留首轮失败和原题复跑结果。增加少量未参与调词的表达及无关问题，避免只验证对固定题的适配。

不新建检索引擎，不扩充无依据关键词，不把召回通过写成回答正确或访问控制已验证。机器人部署、版本回读与权限测试属于接入阶段，不进入本轮性能优化实现。

### 盘点对账

在现有盘点指引中明确：保留范围内材料的具名去向、未覆盖差集、排除理由与触发例外证据；同值材料可引用原件，不重复扩写。集合差集闭环不代替能力与触发行为取证。

第一轮不移植任何私有项目脚本。已有公开通用检查可直接复用；缺少通用接口的对账自动化另行评估，不扩大成本。

## 8. 有意义的回放与回归

公开夹具使用合成项目或已有公开源码，不复制私有正文、模块 ID、服务名、源码片段或日志。通用行为检查至少覆盖两种不同技术栈，流程不得依赖特定语言或框架名。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 稳定输入批次 | 优化前后真实影响集合与最终门禁结果一致；已有全局零结果后不再逐模块取得空队列 |
| 草稿结构错误 | 来源版本、接口匹配及 FAQ 结构错误在预检暴露；修复后预检与正式检查对共同检查项结论一致 |
| 高影响语义错误 | 结构通过但条件或金额等结论错误仍由真实复核阻断；预检不自动确认、批准或改风险等级 |
| 共用事实变化 | 生产者及已知跨模块消费者进入复核；未登记关系不能被解释为无影响 |
| 新增、修改、删除 | 各类变化均使旧结果失效；删除引用也需审核旧答案的处理 |
| 冻结后发生写入 | 旧报告不用于新输入；修改正式文件、配置、关系或新增未跟踪正式文件均被识别 |
| 中断及换执行者 | 从现有检查点恢复，不复制状态系统、不跳过未完成复核、不重复批准 |
| 预检只读性 | 运行前后项目内容无变化；原有待复核和未批准状态保持 |
| 双语言及 full/compact | 对应命令与手顺一致，不要求新增中文或英文专用审核流程 |
| 候选检索 | 在隔离候选中复现标题/关键词漏项；原题及保留题复核，正式快照不被修改 |

高影响语义回放中，自动断言只能检查是否保留未关闭发现和未批准状态；是否正确理解源码仍需实质审读。人工填写“通过”不作为性能实验的质量证明。

### 性能计量

1. 用同一组冻结输入、同一工具基线、同一机器和相同并发设置比较两种流程；采用隔离副本，统一恢复起点，不影响现有知识项目。
2. 先用约 12 模块的合成批次检查调用安排，再用约 96 模块的合成集合观察规模效应。规模仅为实验参数，不代表生产覆盖或真实业务复杂度。
3. 分开记录命令数量、命令起止时间、批次墙钟时间、审核/返修节点。并发命令累计时间不能当作墙钟节省；不推算人工工时。
4. 确定性计时可采用交替顺序的三次回放，报告中位数及范围；不为得到更好数字反复试跑。完整语义审核不因计时重复三次。
5. 允许的结论是实测调用减少和已测场景耗时变化；若端到端改善未证实，则明确只减少了重复检查。不预设百分比、不承诺大型项目显著提速。

## 9. 分步实施与收口

### 第一步：手顺对齐

完成 BR-01 和 BR-03 的中英文说明，补 BR-04 的现有能力入口。逐条核对 runner、Skill 和发布指导没有互相冲突；以公开小批次回放证明可以按说明执行。不先增加新调度代码。

### 第二步：预检实现

抽取无副作用的候选结构检查、接入薄命令和针对性测试。正式 `prepare` 继续完整重验；通过共同错误样本及只读性检查后，再更新使用示例。

### 第三步：回放、审查与发布准备

完成跨模块、删除、旧结果失效、恢复及性能回放，保留可重现结果。代码稳定后跑一次完整回归；只有新增修改、失败或未决风险才补跑相关测试，不在每次文案调整后重复全量回归。

发布前按仓库当前 CI 配置完成支持的 Python 版本检查，检查中英文链接、CLI 帮助与公开内容。报告实际变化、收益和限制；不得把私有项目材料作为公开夹具或附件。

本计划不创建标签、不推送、不发布。版本号、PR 与 Release 在实现及验收完成后按明确授权处理。

## 11. 实施中的范围收敛

- FAQ 复用现有 `index_sections` 给出实际导航标题预览。当前实现没有独立的“问题标题质量”门禁，本轮不添加命名正则或把导航预览说成召回通过。
- 预检不要求四类问答先填“通过”，也不验证语义质量记录完成；结果明确列出这些未检查项。正式 prepare 保留原有问答、语义与影响检查。
- 接口/方法目录、来源版本和调用匹配表一致性复用候选检查。完整匹配状态与部署证据、跨模块引用、关系和审核仍由正式流程校验。
- `document_content_sha256` 是被读取文档文本的辅助摘要，不是全量输入证书，不认证配置、外部依赖或检查期间无并发写入。批次冻结与结果复用仍遵守第 3 节；本轮不新增自动冻结或缓存系统。
- 现有检索评测依赖已审核的基础发布。批准前只前移标题、关键词、题集审阅；自动门禁继续使用取得授权后的 `publish --with-retrieval` 暂存评测。没有新增“未批准草稿发布”通道，也不修改已发布目录试跑。
- 本轮不改 runner 的任务依赖或内置检查；批次建议不能用来跳过 runner 的任务完成条件。性能回放只度量手动 CLI 批末重复调用这一段。
- 回放脚本为 `scripts/benchmark_batch_review.py`，使用公开测试夹具创建临时合成项目，不接受真实项目路径。准备夹具的操作不计入耗时；测量不包含内容审核、返修、prepare 或发布。

正式结果、手顺与自动检查的边界见[验收记录](batch-review-efficiency-results.md)。Python 多版本 CI 属于推送后的发布准备，不能以本机单版本检查代替。
