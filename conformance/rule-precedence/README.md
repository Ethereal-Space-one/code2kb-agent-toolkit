# 预约书送修：条件重叠时怎样回答

这个自编例子用一个问题区分两件事：**哪条规则决定去向，哪条规则仍会留下备注？** 如果只查“有预约”和“需修补”各自成立时的情况，可能答成“有预约就进预约柜”，也可能答成“送修就没有预约备注”。两者都错，但不能靠找到“预约”“修补”两个关键词来区分。

- [输入源码](sources/returns.py)：只生成处理建议，不连接实际书库；第 5 行形成预约备注，第 6–7 行在需修补时返回，第 8–10 行只决定剩余情形。代码能说明建议内容，不能证明实体送达、已通知或后续转运。
- [业务回答](knowledge.md)：保留一个用户能直接检索的问题、两种条件同时成立时的结论、四种输入的对照及现场未知。此处表格供这个小例子演示，不给项目新增必填表。
- [可执行回归](../../validation/tests/test_rule_precedence.py)：锁定本例源码摘要，逐行将业务表中“去向”和“备注”与实际内存返回值分别比对；再用两份刻意写错的解读验证题目能区分什么。

没有条件、只有预约、只有修补三组对照均不能淘汰上述两份错解；补上“有预约且需修补”后，两份各错一项：前者去向错，后者备注错。这个反例说明为什么值得查一次有实质影响的重叠，不代表所有规则都按先命中者胜出，也不要求遍历所有条件组合。遇到条件互斥或取决于缺失的运行配置时，不编造可达场景或线上优先级。

复现（仓库根目录，标准库，无网络）：

```bash
python3 -B -m unittest discover -s validation/tests -p test_rule_precedence.py -v
```

这是公开的开发回归例，不是独立留出题、模型回答实验或生产观测。测试检查表格中的条件与结果，不自动评判相邻自然语言。独立评测时，先固定未见源码和答案键，只给提取者源码、业务问题及当前[取证手顺](../../skills/extract-app-knowledge/contracts/extract.md)，保留其原始回答，再按条件、结果、副作用和未知分别判定。
