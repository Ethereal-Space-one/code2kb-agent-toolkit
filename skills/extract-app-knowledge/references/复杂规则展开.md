# 复杂规则的可推演交付

适用于中间计算、状态转换、区间判定等会改变用户答案的逻辑。简单透传和不影响结果的辅助步骤不启用。不新增固定章节、配置字段、协议、门禁或审核角色；复用既有事实、待核查事项、业务/研发正文及问答自测。以下约定同样适用于英文知识正文。

## 先从消费结果反追各字段

1. 固定入口、源码版本、决策范围与可达分支。指出哪个输出依赖哪个变换，以及哪个字段不参与某项判定。区分临时值、对外输出、持久化状态。
2. 同一步中，字段的条件、公式、取值时机或未命中行为不同，就分行取证，不能只记「分别调整」。每条写清输入来源（原值、前一步新值或配置）、命中条件与优先级、公式或动作、未命中的原值/回退、作用范围及已知副作用。只有代码确有相关行为才记单位、开闭端点、舍入和上下限。
3. 原样记录已知的运算顺序。只有已触发的运行配置实值未知时，把实值保留为变量；若连计算本身也看不到，标明断在何处，不能反推公式。条件不可达、不适用、无变化和未知分别写明，不把一种当另一种。
4. 用原有事实 ID 与固定提交锚点对账。只有多个字段确实共享条件、计算和消费边界时才合并；图、问答和正文不能分别发明规则。

## 呈现方式按逻辑选择

- 总流程只保留主要入口、出口和会改变结果的顺序；详细决策放在现有规则或问答主题下。多个条件决定结果时用决策表，数字规则用符号公式和边界算例，顺序依赖才画子流程。图不是唯一载体，关键结论须有纯文本可读表达。
- 可选表头（非协议）：字段或判断｜何时适用｜原值到新值｜否则｜接着如何使用。没有需要保留的数据，不凭模板补齐。业务版不用代码路径或内部 ID；研发版对应同一规则、补固定源码依据。
- 会一起回答同一问题的公式、边界、回退和未知放在**同一个正文主题**，别只在另一节、图内或脚注写决定结果的条件。超出合理篇幅就按可独立回答的主题拆分，每个主题自带必要前提；不要为了共存而强行把整篇塞进一个单元。

## 复核从题目做起

- 独立查固定源码，选一组能推演的输入；核对无调整、条件等值、多个变换叠加、异常或未知中适用的情况。不必枚举不影响结果的组合。对区间，分开回答「何时形成空档」与「出现空档后如何处理」，并检查实际比较的端点。
- 在既有问答自测中记录预期和证据；一条只写「分别调整」的摘要即使有锚点，也不能作为复杂规则复核通过的依据。若业务所需细节无证据，保留缺口和能答的部分，不补猜测。
- 回放记录分开写：发布正文有无规则，实际召回是否同时带全必要条件和边界，模型是否据此正确采纳。测试夹具中的短语检查不是通用语义门禁，不能替代独审或原生模型实测。

[合成阈值样例](../../../conformance/field-transform/README.md)只说明用法，不代表任何生产规则。

## 更新其中一条计算时

- 先固定新旧源码提交，用同一个边界输入各推一遍。修订受变更影响的事实、决策表、算例和问答；依赖两个端点的结论只要其中一端变了也要重算。独立且不受影响的事实不改写。源码提交更新与语义变化分别记录。
- 修正文前后都看 `impact`。现有复核按文件摘要保护：改动某个正文文件后，该文件上的其他投影也可能进队列。这是重新核对共用文件，不等于每条公式都变了；不能因此漏掉同文件相关事实，也不要为了让队列变短把必需条件拆出同一可答主题。
- 切换新快照前把旧发布完整提交到 Git。审核并发布新快照后回放同一道题，核对新公式和边界值是否同时召回、旧公式是否退出当前结果，再从旧 Git 快照独立查一次可审计性。
